# Review after the private application pilot

30 October 2026 · Separate review of repository documentation, skill guidance and private pilot evidence · Decision: **conditional review**.

This record is sanitized. Application identities, infrastructure names, internal addresses, package versions, raw findings and run traces remain private.

## What changed since the first preview

The private pilot exposed an important scope gap: recurring container configuration checks did not satisfy the request to monitor newly emerging application vulnerabilities. The application builder now prioritizes deployed dependency identity, current advisory/exploitation sources, affected code/configuration paths, vendor fixes or mitigations, and retest evidence. Posture checks remain supplemental.

A separate private executor inventories installed distributions, queries exact versions against OSV, enriches CVE aliases with CISA KEV and retains findings. A local model interprets those facts using a generated application skill. A scheduled completion was observed, along with selected deployed-file/source comparisons and a fresh same-host watchdog result. The executor, application profile and evidence are not bundled in the public download.

The review also found stale public documentation: mismatched package versions, statements that no application had been assessed, references to an unselected public release location, and foregrounding a separate ITSM product despite the intended krnali Ops destination. Those statements are corrected. Existing releases are immutable snapshots; updated packages receive new versions.

## Lessons carried into the reusable skill

- Keep trusted skill instructions separate from application, repository and advisory data in a generated model runner.
- Treat unassessed reachability as unknown. It cannot support non-use, not-applicable status or closure.
- Report inference completion separately from useful, accepted reasoning. Schema validity and instruction echoes do not establish a successful security review.
- Retain findings when state, inventories, feeds or model analysis fail. Demonstrated executor defects need regression checks.
- Group aliases while retaining original IDs; newly observed findings are not necessarily newly published vulnerabilities.
- Use an existing authorized operator destination. krnali Ops is intended for our pilot; delivery has not been implemented or verified, and another ITSM product is unnecessary.

The private runtime's recorded 16 tests and six targeted regression probes cover its implementation corrections. They are separate from this repository's 34 tooling tests and do not establish general vulnerability-detection accuracy. The public application builder now has 19 planned scenarios and eight trigger cases; its 46-call plan validates, but these model evaluations have not been run.

## Release and operating limits

The downloads contain reusable instructions, references and engineering tooling. They do not install a monitoring service. Collectors, inventory coverage, freshness policy, executor privileges, persistent state and operator delivery need application-specific configuration and verification.

No broad code audit, complete infrastructure coverage, live Ops adapter, autonomous patching or discovery of undisclosed zero-days is claimed. Advisory matching can identify disclosed affected-version evidence; source review and runtime observations are required to assess exposure. No-match results and KEV non-membership do not establish safety.

All operational hosting must follow the user's approved destination and policy. This repository's CI performs validation only. Public reuse licensing remains awaiting an owner decision.
