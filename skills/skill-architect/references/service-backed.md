# Service-backed skill boundaries

Use this reference when a skill orchestrates MCP, CI, credentials or operational changes.

Map responsibility before adding tools: agent instructions select and explain a workflow; authenticated services validate identity and object access; the authority owner grants scope; a trusted executor enforces exact effects; independent observations support outcome claims. A host confirmation dialog or skill instruction is not an authority grant.

Reuse one service contract across related skills. Discovery is not permission, a proposal is not approval, dispatch is not execution, and execution is not verified outcome. Unknown, refused and incomplete results must survive every adapter.

Customer-controlled enforcement must verify independent authority, scope, freshness and exact effects. Object/verb permissions alone may not restrict patch values. Evidence provenance does not prove the truth of every producer statement. Credential acceptance, issuance and signing remain domain services.

Capture supported capabilities, current implementation versus proposed tools, credential custody, tenant/actor binding, idempotency, recovery, expiry/revocation limitations and required evidence. Never create executable-looking tools for capabilities that do not exist. Keep target enrollment, approval roots and broad administration outside the model tool catalog.

Apply the actual project's deployment policy and keep destinations explicit in generated deployment configuration. Existing cloud examples or marketplace plans are not deployment authorization.
